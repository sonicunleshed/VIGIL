# Architecture

## Components

- **services/api** — FastAPI app (`app.main:create_app`). Sync SQLAlchemy sessions run in the
  threadpool; a process-wide `write_lock` serialises every write so event ordering is
  deterministic on SQLite.
- **apps/web** — Next.js App Router client. Fetches REST snapshots and refetches on SSE events.
- **packages/contracts** — `openapi.json` dumped from FastAPI and TypeScript types generated by
  `openapi-typescript`. The Pydantic models are the single source of truth.

## Time

The **simulation clock** is the only "now". `ingested_at`, data age, clinician action timestamps
and audit times all use it, so a run with the same seed and the same sequence of clock commands
reproduces identical state. Scenario timeline: patients arrive 10–120 min before `t0`
(2026-01-15T14:00Z); reset releases everything delivered up to `t0`; the clock then runs to
`t0 + 3h` via `step` or `start` (speed = simulated seconds per wall second).

## Data flow

```
scenario_deliveries (deliver_at, event_id order)
   │ advance_to(until)
   ▼
ingest_observation / ingest_symptom_report
   ├─ idempotency: event_id → same payload = duplicate, different payload = 409
   ├─ validation: schema, unit per kind, plausibility bounds, UTC-aware, not ahead of clock
   ├─ events (immutable envelope, seq, out_of_order flag, duplicate_deliveries counter)
   └─ observations / symptom_reports (typed rows)
   ▼
detectors.engine.process → alerts (dedup/cooldown)
   ▼
broker.publish → SSE subscribers (observation, symptom_report, alert_created, …)
```

## Event envelope

`events` holds `event_id` (UUID), `seq` (ingest order), `patient_id`, `event_type`,
`occurred_at`, `ingested_at`, `source`, `scenario_id`, `payload` (canonical JSON as submitted),
`out_of_order`, `duplicate_deliveries`. Rows are never updated except the duplicate counter.

## Ordering rules

- Reads sort by occurrence time then id (`observed_at, event_id`). "Latest value" therefore
  ignores late or out-of-order deliveries that are older than what is already known.
- Out-of-order = an earlier-timestamped event of the same patient+kind stream arrives after a
  later one. It is stored and flagged, never dropped or reordered in storage.
- Alert actions carry a per-alert `seq` so actions in the same simulated instant keep order.

## SSE

In-process `Broker` with one bounded queue per client. `publish` is thread-safe
(`call_soon_threadsafe`). A client that falls more than 1000 messages behind gets one `resync`
message and should refetch snapshots. Disconnects and cancellations always unsubscribe.
Heartbeat comment every 15 s.

## Migrations

Alembic (`services/api/alembic`). The app runs `upgrade head` on startup;
`tests/test_migrations.py` asserts the migrations match the ORM models.

## Decisions taken for ambiguity (simplest deterministic choice)

| Question | Decision |
|---|---|
| Who assigns `event_id`? | Client, required — makes retries idempotent. |
| What is "now"? | Simulation clock, including for API-posted events. |
| Reset vs audit immutability | Reset wipes the run (including its audit log) and writes `simulation.reset` as the first audit entry of the new run. No API updates or deletes audit rows. |
| Patients | Registered at reset (all have arrived before `t0`); not created via events. |
| Vital kinds | heart_rate, resp_rate, spo2, sbp, temp — one event per measurement. |
| Resolve without acknowledge | Allowed (open → resolved); acknowledge after resolve is 409. |

## Web app (apps/web)

- **One store.** `src/lib/store.tsx` holds patients, alerts and simulation state for every page.
  SSE events trigger a coalesced snapshot refetch (no hand-patched state), so all screens agree
  with each other and with the API. The connection indicator never says "Live" unless the
  stream is connected.
- **Pure display logic** lives in `src/lib/` (`monitoring.ts`, `queue.ts`, `timeline.ts`,
  `evidence.ts`) and is unit-tested. Components take typed data and callbacks.
- **Monitoring status** is a published mapping of a patient's unresolved alerts (shown in the UI
  legend): prompt-review alert → urgent review; observed-change or patient-report alert →
  reassessment due; only stale/quality alerts → information gap; none → monitoring (explicitly
  "not a statement that the patient is stable").
- **Charts** plot only real observations; the line breaks where readings are more than 40 min
  apart (a display setting, not a clinical threshold). Questionable readings are hollow dots.
- **Stack choice.** Tailwind with small in-repo primitives (`components/ui`) instead of shadcn/ui,
  lucide icons, Recharts, local Geist fonts (no network at build or runtime).

### Detector evidence contract

The evidence panel reads `alert.evidence_json` defensively:

```json
{
  "event_ids": ["<observation event ids the alert cites>"],
  "rules": ["human-readable rule that fired, with its demo threshold"],
  "limitations": ["what this alert could not account for"],
  "baseline": { "optional": "baseline values used" }
}
```

New alerts are published as `alert_created` SSE events.

### Backend gaps the UI spec needs

| UI spec item | Missing backend piece |
|---|---|
| "Mark reassessment started" action, `reassessment_started` status | New alert action + status |
| Simulation Lab scenario selector (stable / gradual / abrupt / missing) | Per-archetype scenario templates; today one mixed template exists |
| Diastolic BP | Not in the observation vocabulary (systolic only) |

## Detectors (services/api/app/detectors)

Pure functions over an in-memory `PatientHistory`, so live detection and replay share
code. All numbers live in `config.py`.

| Detector | Role | Logic |
|---|---|---|
| `threshold` | Replay baseline | Latest reading of a vital outside a demo limit. Counts questionable readings. |
| `trend` | Replay baseline | Per vital: Theil–Sen slope over 75 min (≥ 3 points) and change from baseline (median of first 2 readings) both past demo values. Quality-blind. |
| `hybrid` | **Live alerts** | Limits + trends on good-quality readings only; ≥ 2 changed vitals (or limit and trend on one) → prompt review; symptom reports → `PATIENT_REPORT`; questionable or out-of-order readings → `DATA_QUALITY` (excluded from change detection); no observation for 45 min → `DATA_STALE`, dated at the moment it fell due. |

**Engine** (`engine.py`). After each ingested event it loads the patient's sorted history,
evaluates the hybrid, and creates alerts through `services.alerts.create_alert`. Each alert
records detector name and version, family (`dedup_key`), evidence event ids, rules and
limitations, and is written to the audit log.

**Dedup.** A candidate is dropped while an alert in the same family is unresolved
(acknowledged still counts), or within the family cooldown after the last one. An open
prompt-review change alert also suppresses a lesser review one. Duplicate deliveries never re-run
detection.

**Determinism.** Observation rounds that share a delivery timestamp are ingested together
before detection, so a round is judged as a whole. Staleness is evaluated before each round
using only data received by then. Alert ids are UUIDv5 of detector, patient, family and creation
time. A test runs the full scenario in one 180-minute step and in 7-minute steps and gets
identical alerts.

## Replay and evaluation (services/api/app/evaluation)

`replay.py` replays a generated scenario through any detector in memory, mirroring the live
pipeline. A test checks that replaying the hybrid reproduces the live alerts exactly. `metrics.py`
scores alerts against scenario labels (definitions in docs/EVALUATION.md). `service.py` builds the
`/api/replay/compare` and `/api/evaluation` responses, caches per seed set, and records each run in
`detector_runs` under a deterministic `run_id`. The web **Insights & Replay** screen shows only
readings *delivered* by the scrubber time, so the chart shows what each detector could see.

## VIGIL Vision

**Browser** (`apps/web/src/lib/vision/`)
- `useCamera.ts`: the camera starts only from a click after the consent box is ticked. All
  tracks are stopped on Stop, unmount, tab hidden, page hide and device loss. Denied,
  unavailable and disconnected states are explicit.
- `usePoseTracker.ts`: loads MediaPipe Pose Landmarker (lite) from `public/` once, GPU with CPU
  fallback. Inference runs about 10 FPS on a cancellable rAF loop. `numPoses: 2` is used only so
  tracking can pause when two people are visible.
- `classifier.ts`: pure heuristics with hold times, hysteresis and cooldowns. Events:
  `person_present`, `person_absent`, `posture_transition`, `significant_motion` and experimental
  `possible_fall_like_motion` ("verify visually").
- `useVisionSession.ts` + `forwarder.ts`: events are sent only while staff have chosen a patient
  and switched on "Send to timeline". They go one at a time, in order, with backoff on network
  errors. The queue is bounded, and each event's fate (on timeline / not sent / dropped) shows in
  the log. Changing the patient or stopping the camera stops the session.

**Server** (`services/api/app/services/vision.py`, `app/api/vision.py`)
- `vision_sessions`: manual patient binding with a random token (only its SHA-256 is stored). A
  new binding for the same patient stops the previous one. Sessions start and stop in the audit
  log.
- `vision_events`: structured events only, sharing the `events` envelope, so retries are
  idempotent on `event_id`. The patient always comes from the session. The browser may echo
  `patient_id`, but a mismatch is rejected. Also enforced: enum event types, `extra=forbid` (no
  image fields), at most 12 primitive features, a 4 KB body limit, ±10 min capture-time skew and
  60 events/min per session.
- Events are stamped at the simulation clock on arrival (never backdated); `captured_at`,
  `session_id` and `model_version` are kept as provenance and shown on the timeline.
- Review policy (`DetectorConfig.vision_review_policy`): by default only
  `possible_fall_like_motion` opens a `CAMERA_OBSERVATION` review request (prompt review,
  10 min cooldown). Everything else is timeline-only. Camera events never feed vital-sign
  detection, staleness or ESI.

## Patient check-in

A patient (or whoever is with them) can tell staff that something changed, from their own phone.

**Server** (`services/api/app/services/checkin.py`, `app/api/checkin.py`)
- `checkin_tokens`: staff create a code for one patient (manual association, like camera
  sessions). The random token is returned once and only its SHA-256 is stored. A new code for the
  same patient replaces the active one. Codes expire `checkin_ttl_minutes` (240) after creation on
  the simulation clock; reset ends them all. Creating and revoking are audited.
- Reports use the existing `POST /api/symptom-reports` with an `X-Checkin-Token` header, so
  ingestion, idempotency and detection are unchanged (the hybrid's `PATIENT_REPORT` rules apply;
  "Get staff help now" sets `urgent_help_requested`). With a code: the report's patient must be
  the code's patient, `source` must be `patient_checkin`, `reported_at` and `scenario_id` must be
  absent (the server stamps the simulation clock), and each code may send 4 reports per 5 wall
  minutes. Without a code, no report may claim the `patient_checkin` source.

**Browser** (`apps/web`)
- Staff pages live in the `app/(staff)` route group, which holds the live store and app shell.
  `/checkin` sits outside it, so the phone never loads the patient list or the event stream.
- The staff **Patient check-in** card (patient timeline) creates a code and draws its QR code
  locally (`components/ui/QrCode.tsx`). The link is `http://<this machine's LAN address>:3000/checkin#<token>`;
  `GET /checkin/origins` lists the addresses (`VIGIL_CHECKIN_ORIGIN` overrides). The token is in
  the URL fragment, which browsers never send to a server.
- A phone cannot reach the API on the laptop's localhost, so `next.config.ts` rewrites exactly
  `/api/checkin/session` and `/api/symptom-reports` to the API, and only when the request carries
  a well-formed `X-Checkin-Token`. The header rule has a value pattern on purpose: without one,
  Next copies the header into the forwarded query string and the code would reach access logs.
  `allowedDevOrigins` lists the machine's LAN addresses so the dev server serves a phone.
- Retries resend the same `event_id`, so a flaky connection records a report at most once.
  `crypto.randomUUID` is unavailable on plain-HTTP LAN pages, so `lib/checkin.ts` builds v4 UUIDs
  from `getRandomValues`.
- The page says what was sent and that staff can see it. It never reassures, promises a wait
  time or mentions priority, and always tells the patient to speak to staff if they feel much
  worse.
