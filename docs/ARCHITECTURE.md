# Architecture

## Components

- **services/api** — FastAPI app (`app.main:create_app`). Sync SQLAlchemy sessions run in the
  threadpool; a process-wide `write_lock` serialises every write so event ordering is
  deterministic on SQLite.
- **apps/web** — Next.js App Router client. Fetches REST snapshots and refetches on SSE events.
- **packages/contracts** — `openapi.json` dumped from FastAPI and TypeScript types generated by
  `openapi-typescript`. The Pydantic models are the single source of truth.

## Time

The **simulation clock** is the only "now". `ingested_at`, data age, clinician action timestamps
and audit times all use it, so a run with the same seed and the same sequence of clock commands
reproduces identical state. Scenario timeline: patients arrive 10–120 min before `t0`
(2026-01-15T14:00Z); reset releases everything delivered up to `t0`; the clock then runs to
`t0 + 3h` via `step` or `start` (speed = simulated seconds per wall second).

## Data flow

```
scenario_deliveries (deliver_at, event_id order)
   │ advance_to(until)
   ▼
ingest_observation / ingest_symptom_report
   ├─ idempotency: event_id → same payload = duplicate, different payload = 409
   ├─ validation: schema, unit per kind, plausibility bounds, UTC-aware, not ahead of clock
   ├─ events (immutable envelope, seq, out_of_order flag, duplicate_deliveries counter)
   └─ observations / symptom_reports (typed rows)
   ▼
broker.publish → SSE subscribers   (detectors hook in here in Phase 3)
```

## Event envelope

`events` holds `event_id` (UUID), `seq` (ingest order), `patient_id`, `event_type`,
`occurred_at`, `ingested_at`, `source`, `scenario_id`, `payload` (canonical JSON as submitted),
`out_of_order`, `duplicate_deliveries`. Rows are never updated except the duplicate counter.

## Ordering rules

- Reads sort by occurrence time then id (`observed_at, event_id`). "Latest value" therefore
  ignores late or out-of-order deliveries that are older than what is already known.
- Out-of-order = an earlier-timestamped event of the same patient+kind stream arrives after a
  later one. It is stored and flagged, never dropped or reordered in storage.
- Alert actions carry a per-alert `seq` so actions in the same simulated instant keep order.

## SSE

In-process `Broker` with one bounded queue per client. `publish` is thread-safe
(`call_soon_threadsafe`). A client that falls more than 1000 messages behind gets one `resync`
message and should refetch snapshots. Disconnects and cancellations always unsubscribe.
Heartbeat comment every 15 s.

## Migrations

Alembic (`services/api/alembic`). The app runs `upgrade head` on startup;
`tests/test_migrations.py` asserts the migrations match the ORM models.

## Decisions taken for ambiguity (simplest deterministic choice)

| Question | Decision |
|---|---|
| Who assigns `event_id`? | Client, required — makes retries idempotent. |
| What is "now"? | Simulation clock, including for API-posted events. |
| Reset vs audit immutability | Reset wipes the run (including its audit log) and writes `simulation.reset` as the first audit entry of the new run. No API updates or deletes audit rows. |
| Patients | Registered at reset (all have arrived before `t0`); not created via events. |
| Vital kinds | heart_rate, resp_rate, spo2, sbp, temp — one event per measurement. |
| Resolve without acknowledge | Allowed (open → resolved); acknowledge after resolve is 409. |
